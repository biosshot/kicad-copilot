# Иерархический лист как чёрный ящик: чтение, соединение и размещение

Статус: проект решения, 2026-09-05. Это спецификация будущего поведения,
не описание реализованных MCP-вызовов. Дополняет
[предложение об областях действия нетов](scoped-nets-proposal.md).

Актуальное решение: пользователь разрешил расширение входного API (вариант B),
сохранив контракты возвращаемых схем. Конкретные JSON-примеры находятся в
[schematic-api-proposal.json](schematic-api-proposal.json). Они заменяют
приведённые ниже предложения добавлять `kind`, `nets`, `boundary_links` в
существующий ответ схемы: такие метаданные выносятся в отдельный контекст.
Для входа выбран `symbols` по аналогии с PCB `footprints`, а не `layout_context`.
Вариант A ниже остаётся описанием ранее рассмотренной альтернативы.

## Основное решение

На родительской странице экземпляр дочернего листа — самостоятельный объект
размещения с прямоугольником и выводами. Внутренние компоненты дочернего файла
не входят в геометрическую сцену родителя. При переходе внутрь листа строится
новая сцена, где его собственные дочерние листы опять представлены чёрными ящиками.

Серверу размещения достаточно геометрии прямоугольника, координат выводов,
соединений и ограничений движения. Файл `.kicad_sch`, содержимое дочернего листа
и KiCad UUID не нужны. Локальный адаптер хранит соответствие между узлом
размещения, экземпляром листа и его физическими объектами.

Сейчас такого входа у HTTP API нет. При строгом требовании оставить сервер
полностью неизменным совместная компоновка должна выполняться на стороне KiCad.
Ниже описаны этот вариант и альтернативное небольшое расширение входного
контракта, позволяющее использовать существующий серверный компоновщик.

## Проверенные ограничения текущего кода

| Участок | Что это означает |
| --- | --- |
| `copilot-server/src/types/circuit.ts`, `CircuitModStruct` | Каждый `add_components` требует 32-символьный каталожный `part_uuid` |
| `copilot-server/src/api/router/mcp-tools.ts`, `ExtractCircuitMcpSchema` | HTTP-вход содержит только `circuit` и `inputCircuit`, входа для произвольной геометрии нет |
| `copilot-server/src/devices/symbols/symbol-parser.ts`, `getSymbol` | Геометрия загружается через EasyEDA по UUID; фиктивный UUID не создаёт символ |
| Там же, `circuitToSymbols` | Компонент без UUID пропускается; список `pins` в запросе не создаёт отсутствующие выводы библиотечного символа |
| `copilot-server/src/agent/completions/index.ts`, `autoPlacement` | В размещение идут добавляемые компоненты; `inputCircuit` служит источником внешних нетов, а не размещаемых прямоугольников |
| `copilot-server/src/circuit-layout/index.ts`, `autoPlaceCircuitWithHierarchy` | Внутренний компоновщик уже принимает `SymbolWithMeta[]` с размерами и координатами пинов; ограничение находится до этого слоя |
| `kicad-copilot/src/kicad/assembly.ts`, `placementOffset` | Символы листов учитываются как занятые прямоугольники; подключения к их выводам и их перемещение не реализованы |

Таким образом, экспортировать псевдокомпонент в `inputCircuit` с
`part_uuid: null` можно в пределах его текущей схемы данных. Это позволяет
адресовать внешнее подключение, но не даёт серверу геометрию для совместного
размещения. Подмена листа случайным разъёмом тоже не решает задачу: размеры,
состав пинов, ориентация и обслуживание такого объекта будут чужими.

## Две модели связности

**Электрическая модель проекта** отвечает, какие пины принадлежат одной цепи
после разрешения иерархических портов, локальных меток, глобальных меток и питания.

**Модель страницы** отвечает, какие объекты видны здесь, какие выводы соединены
именно на этой странице и какие провода/метки нужно сохранить или построить.

Пример: `SH1.OUT_A` и `SH1.OUT_B` соединены проводом внутри дочернего листа.
Снаружи к ним подходят два отдельных провода. Электрический нет у них общий,
но компоновщик не должен из-за этого добавлять перемычку между выводами снаружи.
А если порты связаны внутри через резистор, это вообще два электрических нета:
чёрный ящик не объединяет всё, что относится к одной функции.

Поэтому сохраняются `page_net_id` для соединений текущего листа и
`resolved_net_id` для полного проекта, а также явные группы рисуемых соединений.
Разные `page_net_id` могут иметь один `resolved_net_id`. Глобальное подключение
через метку тоже не обязывает рисовать длинный провод через всю страницу.

Сначала разрешается намерение соединения, затем выбирается доступная точка
и способ изображения. Передавать один плоский список глобальных нетов в layout
и восстанавливать по нему всю геометрию недостаточно.

## Что должен возвращать get_schematic

Вход задаёт корень проекта, физический лист и, если требуется, путь экземпляра.
Сохраняется короткий вызов только с `path`, когда контекст однозначен.
По умолчанию возвращается одна страница; рекурсивное электрическое представление
явно отделяется от неё, чтобы внутренние компоненты не смешивались с родительскими.

В `components` локального MCP-экспорта используются различимые виды объектов
`component` и `sheet`. Это требует обновить локальную схему и её потребителей;
простая передача добавочных полей через прежнюю Zod-схему их не сохранит.
Пример ниже сокращён и не является текущим wire-форматом:

```json
{
  "snapshot": "s42",
  "context": { "file": "main.kicad_sch", "instance_path": "/root-uuid" },
  "components": [
    {
      "kind": "sheet",
      "designator": "SH1",
      "instance_id": "/root-uuid/sheet-uuid",
      "name": "ADC",
      "file": "adc.kicad_sch",
      "part_uuid": null,
      "body_mm": { "x": 80, "y": 40, "width": 50.8, "height": 30.48 },
      "pins": [
        {
          "pin_number": "p1",
          "name": "AIN",
          "direction": "input",
          "at_mm": { "x": 80, "y": 50.8 },
          "side": "left",
          "signal_name": "kcn:v1:net:s42:n17",
          "page_net_id": "pnet7",
          "resolved_net_id": "n17",
          "connected_on_page": true,
          "child_binding": { "label_name": "AIN", "status": "matched" }
        }
      ]
    }
  ],
  "page_connections": [
    {
      "page_net_id": "pnet7",
      "endpoints": ["R1.2", "SH1.p1"],
      "representation": "wire"
    }
  ],
  "boundary_links": [
    {
      "endpoint": "SH1.p1",
      "child_label": "AIN",
      "child_endpoints": ["/root-uuid/sheet-uuid/U2-uuid:3"],
      "resolved_net_id": "n17"
    }
  ]
}
```

`SH1` — выданный адаптером псевдоним, уникальный среди объектов этой страницы.
Он не означает настоящую деталь и не создаёт запись в BOM/PCB. Адрес хранится
по UUID экземпляра; перестановка объектов не должна перенумеровывать псевдонимы
внутри снимка. `p1` связывается с UUID вывода листа, а не с его индексом в файле.
Человек видит `SH1.AIN`, но при одинаковых именах используется точная ссылка.

Сопоставление с дочерними метками ведётся по правилам KiCad: имя/тип интерфейса,
конкретный экземпляр и соответствующие объекты. Несколько одноимённых меток
внутри ребёнка могут соответствовать одному интерфейсу. UUID родительского
вывода и дочерней метки не обязаны совпадать.

Состояния портов различаются: соединён снаружи, соединён только внутри,
отсутствует соответствующая метка/вывод, несовпадение интерфейса. Неиспользованный
вывод сохраняется в экспорте даже при отсутствии компонентов в netlist.
При отсутствии физического вывода дочернюю метку показывают как несогласованный
интерфейс, а не как уже существующий вывод чёрного ящика.

Глобальные неты внутри ребёнка можно показать в сводке `global_access`, но
не дорисовывать ради этого несуществующие выводы листа. По запросу раскрывается
трасса `R1.2 → SH1.AIN → дочерняя AIN → U2.3`. Полное содержимое всех детей
не нужно включать в каждый ответ.

## Операции над листом и его интерфейсом

Компонентоподобный вид используется для адресации и размещения. Операции
с жизненным циклом листа остаются различимыми от замены каталожной детали:

| Намерение | Действие |
| --- | --- |
| Подключить `R1.2` к `SH1.p1` | Изменить провод/метку на родительской странице; child-файл не изменяется |
| Вывести внутренний нет наружу | Создать метку в ребёнке и согласованный вывод соответствующего символа листа у родителя |
| Соединить два дочерних листа | Связать их выводы на странице родителя |
| Соединить листы разных ветвей | Построить цепочку интерфейсов до общего предка и соединить там; существующие подходящие порты переиспользовать |
| Переместить `SH1` | Переместить его прямоугольник, подписи и выводы, затем восстановить прилегающие провода |
| Изменить форму/порядок выводов | Явно изменить геометрию интерфейса и перестроить затронутые провода; логические привязки сохраняются |
| Заменить дочерний файл | Отдельная операция с явной картой старых и новых портов; это не `replace_components` по part_uuid |
| Удалить экземпляр листа | Явно удалить символ и обработать его внешние соединения; общий файл не удалять автоматически |

Вход и выход задаются относительно содержимого дочернего листа: родительский
sheet pin сохраняет согласованный с hierarchical label тип, а не инвертирует
его как электрическую роль подключаемого компонента.

К неизвестному порту нельзя молча подключиться глобальным нетом с похожим именем.
Для создания новых интерфейсов адаптер сначала строит полный список изменений,
после чего проверяет и записывает все затронутые файлы одной восстанавливаемой
операцией. Порт без внутреннего подключения допустим как явно создаваемый
интерфейс, но возвращается с этим статусом.

## Совместное размещение: геометрия и ограничения

Общая сцена страницы содержит реальные компоненты, чёрные ящики дочерних листов,
интерфейсные точки самой страницы и сохранённые объекты/провода.
Листы без выводов тоже участвуют как прямоугольники.

Размер существующего листа берётся из его исходной геометрии. Размер нового
определяется количеством выводов по сторонам, шагом сетки, длиной имён и
подписей листа. Сначала формируется интерфейс, затем вычисляется прямоугольник,
после этого запускается размещение. Площадь содержимого ребёнка не задаёт размер
его символа в родителе.

Для новых интерфейсов исходная эвристика: входы слева, выходы справа,
остальные выводы по заданным группам; это предпочтение, не запрет другой формы.
У существующих листов стороны и порядок сохраняются, пока не запрошено их
изменение. Перестановка выводов требует нового расчёта маршрутов.

При обычном добавлении компонента существующие листы и невыбранные компоненты
зафиксированы. При явной компоновке страницы выбранные листы и компоненты
двигаются совместно. Пересборка всех компонентов сама по себе не разрешает
двигать листы. Геометрия внутренних компонентов не изменяется от движения
родительского прямоугольника.

Для первого выпуска у листов разрешается перенос с сохранением ориентации,
без автоматического зеркалирования. Любое дальнейшее разрешение вращения требует
согласованного преобразования корпуса, всех выводов и текстов с проверкой KiCad.
Серверные эвристики вращения деталей по GND не применяются к чёрным ящикам.

Маршруты рассчитываются к фактическим координатам выводов с учётом прямоугольников,
зазоров для текста, проводов и junction. Совпадение имён net не заменяет попадание
конца провода в контакт. Пересечение проводов разных цепей не получает junction;
неоднозначные наложения и проходы через пины отклоняются.

`elk.portConstraints = FIXED_POS` фиксирует координаты портов внутри узла,
но не координаты самого узла на странице. Текущий API не реализует произвольные
неподвижные препятствия для общего размещения. Режим фиксированных объектов
нуждается в отдельной локальной логике либо в явно поддержанном серверном пути;
игнорировать ограничения движения недопустимо.

## Вариант A: сервер и HTTP-контракт полностью неизменны

1. KiCad строит модель страницы и разрешает все подключения к sheet pins локально.
2. Существующий сервер размещает только реальные добавляемые/пересобираемые
   компоненты. Чёрные ящики в `inputCircuit` могут давать контекст внешних нетов,
   но не считаются результатом размещения. Запросы только с листами сервер
   вообще не требуют.
3. Локальный компоновщик объединяет символы листов и полученные группы деталей.
   Готовая группа может переноситься целиком с сохранением внутренних проводов;
   отдельные компоненты могут стать самостоятельными узлами по своей KiCad-геометрии.
4. Локальный маршрутизатор строит внешние соединения между реальными пинами,
   выводами листов и границами групп. Серверные временные NETPORT заменяются
   целевыми точками подключения, а не глобальными метками.
5. Writer записывает нативные объекты KiCad и проверяет полученный проект.

Для группы учитываются выходы реальных пинов и свободные коридоры к границе.
Нельзя просто спроецировать внутренний пин на край прямоугольника и провести
через детали прямую линию. Если внешние трассы не помещаются, группа переразмещается
или результат отклоняется. Сохранённые серверные провода не масштабируются.

Этот вариант соблюдает исходное ограничение буквально, но требует нового
локального компоновщика и трассировки соединений схемы. Существующий
`placementOffset` не выполняет эту работу: он только ищет перенос готового блока.
Прямого способа заставить текущий удалённый API разместить произвольный
многовыводной лист нет. Это ограничение не обходится сменой `signal_name`.

## Вариант B: общий сервер получает универсальные узлы с геометрией

Если допустимо расширить вход без перестройки архитектуры сервера, добавить
необязательный `layout_context`. Он описывает абстрактные узлы и требуемые
соединения, а не KiCad-файлы. Прежние вызовы сохраняют прежнее поведение.

Предлагаемый фрагмент запроса, геометрия в существующих серверных единицах:

```json
{
  "layout_context": {
    "nodes": [
      {
        "designator": "SH1",
        "width": 200,
        "height": 120,
        "pins": [
          { "pin_number": "p1", "name": "AIN", "x": 0, "y": 40,
            "signal_name": "KCN000001" },
          { "pin_number": "p2", "name": "DATA", "x": 200, "y": 80,
            "signal_name": "KCN000002" }
        ],
        "placement": { "mode": "movable", "allowed_rotations": [0] }
      }
    ],
    "connections": [
      { "source": "R1_pin_2", "target": "SH1_pin_p1",
        "signal_name": "KCN000001", "representation": "wire" }
    ]
  }
}
```

`circuit.add_components` по-прежнему содержит только настоящие детали с UUID.
Геометрические узлы добавляются во внутреннюю сцену после поиска компонентов.
Им не требуется выдумывать UUID или ослаблять требование UUID у настоящих деталей.
Идентификаторы узлов проверяются на конфликт с реальными designator и служебными
идентификаторами; набор пинов и net-контекст должны совпадать с электрической
проекцией того же запроса. Габариты, координаты и число объектов валидируются.

Внутри сервера требуются конкретные изменения:

- Принять и пронести `layout_context` через workflow; не терять его при Zod parse.
- Создать для абстрактного узла `SymbolWithMeta` напрямую. Не запускать поиск
  деталей, `getSymbol`, разбиение секций и замену компонента по нему.
- Добавить узел и его метаданные во внутреннюю `Circuit` и построение результата,
  чтобы он получил `pos`, а его пины сохранили ссылки в `edges`.
- Исключить абстрактные узлы из шаблонов усилителей/фильтров и эвристик вращения
  реальных деталей; применить объявленные ограничения движения.
- Сохранить явные `connections`: существующие `searchExternalSignals` и
  short-symbol preprocessing могут заменять связи метками. Для соединений
  `representation: wire` такая замена запрещается.
- Не обещать `fixed` до реализации такого режима. Сервер обязан отклонить
  неподдерживаемое ограничение; клиент выбирает локальную компоновку варианта A.

Одного изменения `circuitToSymbols` недостаточно: разбиение, шаблоны, генерация
служебных портов и обратная сборка также должны знать, что узел имеет явно
заданную геометрию. При этом понимать иерархию KiCad серверу не требуется.

Результат можно сохранить в существующей форме `CircuitAssembly`: абстрактный
узел возвращается в `components` с `designator`, `part_uuid: null`, `pins`, `pos`,
а соединения — в `edges`. Локальная таблица запроса отличает его от настоящей
детали. Привязка к `sheet UUID`, child file и pin UUID остаётся у клиента.
Никакого поиска устройства или конвертации EasyEDA2KiCad для такого результата
не происходит. Формат ответа допускает nullable UUID, но весь путь его обработки
надо явно реализовать и проверить.

Рекомендуемый способ при выборе B — отдельный необязательный контекст узлов,
а не прятать JSON-геометрию в `search_query` или регистрировать фиктивные детали
в каталоге. Это изменение API, хотя общей архитектуры сервера оно не меняет.
Пока требование «сервер вообще не менять» действует буквально, базовым остаётся A.

## Обратная запись, проверка и пример полного цикла

Пример задачи: добавить R1 между `J1.1` и входом `AIN` дочернего ADC, разместить
R1 и ADC вместе. План страницы содержит цепочки `J1.1 → R1.1` и
`R1.2 → SH1.AIN`. Если AIN отсутствует, сначала формируется его интерфейс и
соединение с явно указанным внутренним пином. Затем рассчитываются габариты SH1,
положения узлов и маршруты к выбранным выводам.

Writer применяет результат по виду объекта. Для детали используется обычный
символ, для SH1 редактируется исходный `(sheet ...)`, для порта — `(pin ...)`.
UUID листа, выводов, `Sheetfile`, instance paths, страницы и прочие свойства
сохраняются. При изменении геометрии учитываются все прилегающие провода,
включая связи с невыбранными компонентами. Новые junction и метки создаются
из плана страницы, а не из предположений по префиксу имени нета.

Сначала создаётся кандидат проекта. Проверка на его корневом листе подтверждает:

1. `R1.2` соединён с целевым внутренним пином ADC через `SH1.AIN`.
2. R1 не закорочен: сети его выводов остались различными.
3. Остальные связи и области действия нетов сохранены, интерфейсы согласованы.
4. Концы проводов попадают в реальные выводы; корпус и подписи не перекрываются,
   нет недопустимых junction, выходов за лист и перемещений фиксированных объектов.
5. Нативный preview показывает читаемый результат. ERC сравнивается с исходным
   состоянием, чтобы обнаружить новые ошибки, а не требовать чистоты чужого проекта.
6. Повторный `get_schematic` возвращает ту же ожидаемую модель страницы и трассу
   связи внутрь ребёнка; это проверяет полный цикл чтения и записи.

После проверок применяется восстанавливаемый набор изменений с проверкой хешей.
Несколько rename не считаются атомарной транзакцией: журнал и откат охватывают
все затронутые файлы. Изменение интерфейса повторно используемого child-файла
затрагивает все его экземпляры и требует согласованного обновления родителей
либо явно выбранного клонирования. Простое движение символа листа в уникальном
родительском файле не меняет геометрию компонентов в child-файле.

В MVP скалярные порты поддерживаются полностью; шины и выражения bus aliases
не заменяются фиктивным одним скалярным пином. Затрагивающие неподдерживаемые
шины операции отклоняются до записи с конкретным указанием участка.

## Критерии готовности и последовательность

Первый сквозной сценарий должен включать родителя, два дочерних листа, реальные
детали на родителе, проводные подключения к выводам листов и локальные одноимённые
неты внутри детей. Проверяется именно размещение и восстановление этой схемы,
а не только сохранность пустых прямоугольников.

Дополнительные сценарии: лист без выводов; неподключённый порт; две копии одного
child-файла; несколько выводов, соединённых внутри ребёнка; вложенность более
двух уровней; фиксированный лист и новый компонент; движение листа с проводами;
добавление/удаление порта; общие глобальные цепи без фиктивных sheet pins;
неизвестный UUID виртуального узла в ответе; сбой при записи двух файлов.

Порядок: модель страницы и get_schematic → нативная запись/соединение sheet pins
→ совместная компоновка одного родительского листа по A либо B → проверки
полного цикла → изменение интерфейсов нескольких уровней и поддержка повторного
использования. Ограничения до готовности соответствующего шага отражаются
в доступных операциях, без молчаливого перехода на глобальные метки.

Рабочая архитектура клиента в обоих вариантах одинакова:
`HierarchyContext → PageGraph → LayoutScene → NativeSheetPatch → ProjectValidation`.
Выбор A/B меняет исполнителя размещения, но не модель листов и нетов.
