# Сохранение локальных нетов и иерархических соединений

Статус: архитектурное предложение, 2026-09-05. Описанный интерфейс пока не реализован.

Актуализация: согласовано расширение входного API с сохранением контрактов
возвращаемых схем. Новые примеры строк сигналов, объектов чёрного ящика и
отдельного контекста — в [schematic-api-proposal.json](schematic-api-proposal.json).
При расхождениях с ранними примерами ниже приоритет имеет этот JSON-проект.

Уточнение после разбора размещения: одного преобразования имён недостаточно для
совместного размещения компонентов и символов дочерних листов. Полная модель
страницы, чёрные ящики и граница возможностей существующего сервера описаны в
[hierarchical-blackboxes-proposal.md](hierarchical-blackboxes-proposal.md).
При полностью неизменном сервере совместное размещение выполняется локально;
для размещения на сервере предлагается отдельное обратно совместимое расширение.

## Решение и граница изменений

Добавить в `kicad-copilot` адаптер между собственной моделью схемы и существующим
контрактом `copilot-server`. Удалённый `/v1/mcp-tools/extract-circuit` продолжает
получать те же `circuit`, `inputCircuit`, строки `signal_name` и возвращать
`CircuitAssembly`. Принадлежность соединений листам, метки и порты остаются
ответственностью локального KiCad-адаптера.

Под «сервером без изменений» здесь понимается общий `copilot-server`. Локальные
reader/writer, MCP-описания, экспорт контекста и проверки KiCad изменяются.
Для создания новых интерфейсов листов потребуется локальная операция с портами;
изменять ради неё удалённый контракт не нужно.

## Что сейчас теряется

- `src/kicad/schematic-reader.ts`: `normalizeSignalName()` превращает корневое
  `/FB` в `FB`. XML-преобразование оставляет у пина только имя результирующего
  нета, без объектов меток и интерфейсов листов.
- `getSchematicContext()` экспортирует дочерний лист отдельно и проект отдельно.
  Эти экспорты имеют разный контекст иерархии. Выбор компонентов по физическому
  `Reference` недостаточен для повторных экземпляров одного файла.
- `src/kicad/assembly.ts`: при `fullPhysicalRebuild` удаляются все провода и
  локальные, глобальные, иерархические метки. Условие проверяет оставшиеся реальные
  компоненты, но не сохранность интерфейсов дочерних листов.
- `signalPortSymbol()` клонирует символ питания VCC. Изменение графики или
  обозначения на `#PORT` само по себе не убирает электрическую семантику питания.
  Резервная ветка подключения непосредственно создаёт `global_label`.
- `src/circuit/extract.ts`: проверка результата сравнивает строки только для
  явно заданных внешних подключений. `beautify.ts` не сравнивает связность до и
  после пересборки. Успешный экспорт netlist подтверждает читаемость, но не
  сохранение электрической схемы.
- `docs/schematic/project-and-sheets.md` прямо предписывает глобальные соединения,
  поскольку создание листа пока не создаёт его иерархические выводы.

## Модель: электрический нет и способы подключения к нему

Одного поля `scope: local | global | hierarchical` у результирующего нета мало.
На одном электрическом нете могут находиться разные метки и порты. Например,
выход `OUT` дочернего листа подключён через вывод листа к `ADC_IN` родителя.
Это один электрический нет с разными именами в точках доступа.

Нужны три связанные сущности:

1. **Экземпляр листа:** путь UUID от корня, физический файл, родительский
   экземпляр, UUID символа листа. Имя листа используется для отображения.
2. **Электрический нет:** ссылка в снимке проекта, точное результирующее имя
   KiCad, множество подключённых пинов и точек доступа.
3. **Точка доступа:** экземпляр листа, вид (`label`, `global_label`,
   `hierarchical_label`, вывод листа, символ питания, провод/пин), локальный текст,
   UUID объекта, координаты и направление, когда они применимы.

Идентичность компонента — путь экземпляра листа плюс UUID символа; пина — эта
идентичность плюс номер пина с учётом секций символа. `R1` и название файла
сохраняются как удобные адреса, но не заменяют идентичность.

Не считать имя netlist или числовой код нета постоянным UUID. Ссылка на нет
действует в конкретном снимке. При изменении файлов адаптер повторно разрешает
ссылку по сохранённым объектам; при неоднозначности возвращает ошибку устаревшего
контекста. Слияние и разделение нетов оформляются как явные изменения.

## Экспорт и команды для нейронки

`get_schematic` должен читать связность от корня проекта, затем выбирать нужный
экземпляр листа. Локальный разбор S-expression добавляет метки, выводы листов,
питание и геометрию. XML netlist задаёт результирующую связность, но не заменяет
разбор исходных объектов. Сопоставление учитывает провода, junction и правила
пересечения, а не только совпадение координат концов.

В экспорте оставить `components`, добавить локальный каталог `nets`, `ports`
и контекст экземпляра. У пинов `signal_name` может содержать ссылку из каталога:

```json
{
  "signal_name": "kcn:v1:net:s42:n17"
}
```

Каталог объясняет, что `s42:n17` — например, `FB` внутри `/Power`, и перечисляет
доступные точки подключения. Нейронка копирует ссылку, а адаптер проверяет её.
Нельзя подключиться к локальному нету чужого листа только по знанию его ссылки:
должен существовать доступ через иерархию либо отдельный запрос его создания.

Предлагаемые записи в существующем строковом поле:

| Запись | Значение |
| --- | --- |
| `kcn:v1:net:s42:n17` | Подключиться к существующему нету через доступную точку текущего экземпляра |
| `kcn:v1:local:FB` | Создать или использовать локальный `FB` текущего экземпляра |
| `kcn:v1:global:%2B3V3` | Явно использовать глобальный `+3V3` |
| `kcn:v1:port:OUT` | Подключиться к уже существующему порту `OUT` текущего экземпляра |
| пустая строка / `NC` | Существующие специальные значения для неподключённого пина / no-connect |

Это предлагаемый синтаксис, а не готовые вызовы. Имена после префикса кодируются
через percent encoding; декодирование строгое и однократное. Реальные метки,
совпадающие с зарезервированным синтаксисом или `NC`, доступны через каталог нетов.
Протокольные строки никогда не печатаются на схеме.

Для совместимости существующий обычный `signal_name` разрешается по текущему
контексту, без изменения найденной области действия. В новом режиме для
неизвестного имени требуется явное `local:` или `global:` с полным префиксом.
Старое поведение «неизвестное имя становится глобальным» можно оставить только
в явно выбранном режиме совместимости. Нельзя молча менять смысл старых вызовов.

## Передача через неизменный удалённый контракт

Адаптер строит таблицу соответствия на время операции:

```text
экземпляр Power, локальный FB  -> KCN000001
экземпляр Analog, локальный FB -> KCN000002
глобальный +3V3               -> KCN000003
```

Для уже соединённых через иерархию точек используется один транспортный токен,
даже если их локальные тексты различаются. Токен выделяется по разрешённой
связности, а не простым склеиванием `scope + name`.

Это правило относится к электрическому контексту. Для размещения нужен также
граф соединений текущей страницы: общая электрическая цепь не требует провода
между всеми её точками на родительском листе. Например, выводы листа могут быть
соединены внутри дочернего файла. Группы рисуемых соединений и явные внешние
точки передаются компоновщику отдельно; подробнее — в дополнении про чёрные ящики.

Согласованно преобразуются все существующие пины проекта, добавляемые пины,
`external_connect`, порты reusable-блоков. На обратном пути обрабатываются
`components[].pins`, `added_net`, `rm_net` и служебные компоненты. Ссылки на
служебные компоненты в edges должны оставаться согласованными; нельзя глобально
заменять текст внутри всех строк ответа.

Метаданные хранятся рядом с запросом внутри адаптера. Неизвестный токен в ответе
нельзя автоматически трактовать как глобальный сигнал. Для внутренних нетов,
созданных сервером при раскрытии reusable-блока, нужен отдельный путь импорта:
проверенная принадлежность новому блоку, уникальное локальное имя, отсутствие
связей с нетами вне блока без явно сопоставленного порта. Если происхождение
нельзя установить из ответа, запись останавливается до изменения схемы.

Сервер не полностью безразличен к тексту `signal_name`: в
`copilot-server/src/circuit-layout/short-symbol.ts` есть эвристики GND/VCC,
а в `layout.ts` — специальный префикс `ext_`. Нейтральные токены обходят эти
эвристики, что может ухудшить размещение питания и распознавание шаблонов.
Это нужно измерить при интеграции. Оптимизация может использовать контролируемые
транспортные имена вроде `GND_KCN000004`, выделенные по явно известной роли;
writer всё равно восстанавливает исходный нет по таблице и не доверяет
`part_uuid: GND` как разрешению глобализовать соединение.

Сначала проверяется корректность связности с нейтральными токенами. Сохранение
качества размещения — отдельный критерий выпуска, а не основание убирать scope.

## Обратная запись и границы изменяемого блока

- Локальная точка подключения создаёт обычную `label` с локальным текстом.
- Глобальная точка создаёт `global_label` или подходящий символ питания,
  если такая область действия задана или уже существует.
- Иерархический интерфейс сохраняет `hierarchical_label`, соответствующий вывод
  листа и соединение родителя. Простая локальная метка допустима внутри дочернего
  листа как способ подключиться к уже сохранённому интерфейсу.
- Имя `VCC`, `GND` или `FB` само по себе не определяет область действия.
  Локальная шина питания не должна превращаться в глобальную из-за оформления.
- Провода к сохранённым выводам листов, меткам и внешней части блока являются
  границами пересборки. Их точки включаются в защиту от удаления наравне с пинами
  сохранённых компонентов. При перемещении блока адаптер восстанавливает
  подключения к этим границам.

`fullPhysicalRebuild` нельзя определять только отсутствием оставшихся реальных
компонентов: лист с дочерними листами и интерфейсами не пуст. Пересборка блока
не даёт права удалить интерфейс листа, даже если все компоненты блока выбраны.

Коллизии проверяются по правилам KiCad. Локальная и глобальная метки с одинаковым
именем на одном листе соединяются. Программный `scope` не может сделать их
изолированными: запрос независимого локального нета в такой ситуации должен
получить ошибку коллизии или явное новое имя, а не обещание изоляции.

## Создание новых интерфейсов листов

Отдельная локальная операция принимает экземпляр листа, имя порта, направление
и ссылку на нет родителя. Она создаёт согласованные `hierarchical_label` в
дочернем файле и вывод символа листа в родительском, затем соединяет этот вывод.
Для связи соседних листов путь проходит через их общего предка. Нельзя заменить
его одинаковыми глобальными метками или «глобальной меткой с полным путём».

Одной строки `port:OUT` недостаточно для создания интерфейса: она не задаёт
направление и родительское подключение. Поэтому на первом этапе эта строка
только адресует существующий порт. Создание портов расширяет локальный MCP,
но оставляет общий удалённый сервер без изменений.

Один файл может представлять несколько экземпляров листа. Чтение различает их;
запись файла затрагивает все экземпляры. Выбор экземпляра не делает изменение
файла индивидуальным. До реализации общей правки всех экземпляров либо явного
клонирования файла такие записи должны блокироваться с понятной диагностикой.

При изменении нескольких файлов нужны staging полной иерархии, проверки хешей
исходников, общий checkpoint и журнал восстановления. Несколько `rename` не
образуют атомарную транзакцию: необходим откат всего набора и восстановление
после прерывания. Проверка выполняется на корне подготовленного проекта.

## Проверки результата

Проверять связность всего проекта до записи файлов, а не только строки имён
у изменённых пинов. Для `beautify` множества соединённых пинов и интерфейсы должны
сохраниться. Для `extract` допускаются только изменения из запроса; соответствие
UUID при запрошенной замене компонентов ведётся явно.

Имена netlist могут измениться из-за выбора KiCad канонической метки, поэтому
проверка связности сравнивает группы пинов, а проверка сохранности меток — сами
объекты и их свойства. Экспорт в PCB продолжает использовать точные имена,
выданные KiCad, без транспортных токенов и удаления начального `/`.

Необходимые регрессии:

1. `FB` на двух листах остаются разными после добавления и beautify одного листа.
2. Глобальный `+3V3` остаётся общим, локальный `VCC` не глобализуется.
3. `OUT` дочернего листа остаётся связан с `ADC_IN` родителя после пересборки.
4. Пересборка всех реальных компонентов сохраняет выводы дочерних листов,
   иерархические метки и провода к ним.
5. Корневой локальный `/FB` не смешивается с глобальным `FB` другого листа;
   коллизия локальной и глобальной меток на одном листе обнаруживается.
6. Повторные экземпляры одного файла корректно экспортируются; неподдерживаемая
   запись в общий файл останавливается до изменений.
7. Частичная замена/удаление не разрывает внешний конец общей сети.
8. `NC`, безымянные неты, алиасы, скрытые power-пины и глобальные земли с разными
   именами не теряют смысл. В частности, AGND не превращается в GND.
9. Прерывание операции с двумя файлами восстанавливает согласованную иерархию.
10. Существующие серверные fixtures подтверждают согласованное преобразование
    net-строк, служебных symbols и edge-ссылок; проверяется качество размещения.

Шины требуют отдельного сопоставления членов и портов. Пока оно не реализовано,
операция сохраняет незатронутые шины и отказывается пересобирать затрагивающий их
участок; превращать его в глобальные скалярные метки нельзя.

## Порядок реализации

1. Построить снимок иерархии и связности, экспортировать адресуемые неты/порты.
   При чтении сохранять исходный scope; новые возможности записи ещё не заявлять.
2. Добавить транспортное преобразование и запись локальных/глобальных нетов;
   защитить существующие интерфейсы. Проверку проекта включить в extract и beautify.
3. Добавить локальную операцию создания/соединения портов и запись нескольких
   файлов с восстановлением. Повторные экземпляры и шины расширять отдельно,
   с явными ограничениями до готовности.

Файлы для реализации: `src/kicad/schematic-reader.ts`, новый модуль контекста
нетов/экземпляров, `src/circuit/extract.ts`, `src/circuit/beautify.ts`,
`src/circuit/target-assembly.ts`, `src/kicad/assembly.ts`, schematic writer и
validation, локальные MCP tools и `docs/schematic/*`. Общий `copilot-server`
не меняется. В рабочих схемах существующие глобальные неты автоматически
не переводятся в локальные: намерение прежней генерации из одного имени
достоверно восстановить нельзя.

## Источники семантики KiCad

Правила областей действия меток, соединения одноимённых меток на одном листе
и связи через выводы листов: [KiCad 9, Schematic Editor](https://docs.kicad.org/9.0/en/eeschema/eeschema.html#labels).
Повторные экземпляры листов и связь родителя с дочерним листом:
[Hierarchical schematics](https://docs.kicad.org/9.0/en/eeschema/eeschema.html#hierarchical-schematics).
Выбор результирующего имени:
[Net name assignment rules](https://docs.kicad.org/9.0/en/eeschema/eeschema.html#net-name-assignment-rules).
